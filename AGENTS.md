# AGENTS.md — dmptool-apollo-server

You are a senior backend engineer working on the **DMP Tool Apollo Server (GraphQL API)**, an Apollo Server 5 app written in TypeScript 6. 
It provides GraphQL queries and mutations for the DMP Tool UI `dmptool-ui`, DMP Tool REST API `dmptool-api` and external partners. 
It also makes calls to the DMP Tool Auth service `dmptool-auth` to validate access tokens.

The local development environment uses **Docker Compose** to run the Apollo Server, MySQL database, Redis cache and LocalStack.

These rules apply to every change in this repo.

## Configuration

- Configuration is in `.env` files, `docker-compose.yaml`, `config/*.json`, and `config/*.yaml`. Don't hardcode config values in code. Use `process.env` or the `config` package to access them.
- When making changes, keep in mind that when this application is deployed into our production environment, it will be running in a Docker container with a read-only filesystem. The ENV variables from both the `docker-compose.yaml` and the `config/*.json` files will be fed into the container via ENV variables by our CI/CD pipeline. If you add or change any of these variables please note it in the PR so that they can be updated accordingly.
- This app requires the `dmptool-auth` service to be running on port `4646` in order for it to validate CSRF and access tokens. You can check if the service is running by visiting `http://localhost:4646/healthz` in your browser. If you see a 404 error, the service is not running. If it is not running you may start it by navigating to the `dmptool-auth` directory (which should be adjacent to this project) and run `docker compose up`. If you do not have access to the directory you should notify the development team so that they can either provide you with access or start it for you.

## Apollo context

- The Apollo context is created in `src/app.ts` and passed to resolvers. It contains the `logger` and `dataSources` objects, and is used to pass information between resolvers and middleware. It should not contain business logic or data access code.

## Middleware and Plugins

- middleware lives in `src/middleware`.
- Plugins live in `src/plugins`.
- Middleware and plugins are used by the Apollo Server to handle requests and responses, and to add functionality to the server. They should be used for cross-cutting concerns, such as logging, authentication, and error handling. They should not contain business logic or data access code.

## Database

- The database is a MySQL 8.0 database, accessed via the `mysql2` package.
- It should not be accessed directly by resolvers or services. Instead, use the models in `src/models` or `src/services` to access the database.
- The database schema is defined s defined and modified by the SQL files in the `data-migrations` directory. These files should be executed when the docker compose environment is running. The files in the root of that directory modify the database schema (e.g. add tables, remove columns, etc.), files within the `local` subdirectory contain SQL that manipulates data (e.g. update a specific value in a table). You can run the schema changes with `bash data-migrations/process.sh`. To run the SQL in the `local` subdirectory you can run `bash data-migrations/process.sh local`. Once a data migration runs successfully, an entry is added to the `dataMigrations` table. This prevents migrations from being executed more than once.

## Logging

- Use the `logger` object from the Apollo context to log messages. It is a Pino logger that is configured to log to stdout in JSON format. It is used by the Apollo Server to log requests and responses, and to log errors. It should be used for logging messages that are relevant to the request being handled. It should always include the JTI and id from the current user's access token.

## Generic helper functions

- place generic helper functions in the `utils` folder.

## Models, Services, Schemas, Resolvers, and DataSources

- models are in the `models` folder, and are used by resolvers to access the database.
- services are in the `services` folder, and are used by resolvers to access external APIs and provide complex business logic.
- GraphQL schemas are in the `schemas` folder, and are used by resolvers to validate input and output data.
- Resolvers are in the `resolvers` folder, and are used to implement the GraphQL API.
- DataSources are in the `datasources` folder, and are used by resolvers, models and services to access the database and external APIs.
- Resolvers should only use the Apollo context to access logger and data sources.
- Resolvers should use the `authenticatedResolver` helper to enforce authentication, and the context specific authorization helpers in the other services to authorize users (e.g. a updatePlan resolver should use the `planService` to check if the user is authorized to update that plan). When you edit a file with older existing resolvers that do not use the authenticatedResolver helper but include authentication logic, update them to use it. Do not add new resolvers that do not use it.

## GraphQL

- After any change to the GraphQL schema files, run `npm run generate` and commit the regenerated `src/types.ts` file. Then run `npm run build`, because schema changes often break resolvers.
- Make a note of any schema changes made in the CHANGELOG and PR description, so that the `dmptool-ui` and `dmptool-api` teams can update their code accordingly.

## Error handling

Errors are handled in 2 ways, depending on whether they are thrown or returned in the response.
For example, a mutation that fails an authentication or authorization check will throw 400 level errors, while a mutation that attempts to update a plan with invalid data will return contextual validation errors in the response.
Contextual errors help the `dmptool-ui` and `dmptool-api` teams display user-friendly error messages in the UI.

To summarize:
- **Thrown errors** (network failures and top-level GraphQL errors) should be thrown as exceptions.
- **Validation errors in the response** come back as data, not as exceptions. Mutations return an `errors` object (e.g. `Plan.errors`).

## Auth

- Tokens are issued by the separate `dmptool-auth` service (RS256). This app only verifies them, using the auth service's JWKS keys (`lib/server/auth.ts`). Never sign tokens here or add a shared JWT secret.
- Tokens are in http-only cookies. The `auth` middleware reads them and adds the decoded claims to the Apollo context. Resolvers can access the claims via `context.token`.
- Authorization checks are done in the resolvers, using the `token` claims and the relevant service functions to determine if the user is authorized to perform the requested action. For example, a `plan` resolver will use the `planService` to check if the user is authorized to update that plan.
- CSRF tokens are also validated by the `dmptool-auth` service. The `auth` middleware reads the CSRF token from the `X-CSRF-TOKEN` header and validates it against the `dmptool-auth` service. Resolvers should not validate CSRF tokens themselves.

## Git and PR workflow

- **Branches:** `feature/<issue#>/<INITIALS>-short-description` or `bug/<issue#>/<INITIALS>-short-description`, cut from `development`.
- **Flow:** feature/bug → `development` → `stage` → `main`. Open feature PRs against **`development`**, never against `stage` or `main`.
- **Commits:** short, lowercase, past-tense summaries that match the history ("added retry logic for CSRF errors", "fixed linting error"). Keep each commit focused on one change.
- **CHANGELOG:** every PR adds a line under the right heading (`Added`, `Updated`, `Fixed`, `Removed`, `Chore`) at the top of `CHANGELOG.md`, ending with the issue number, e.g. `[#366]`.
- **PR description:** Be explicit about the changes that were made. Always highlight any GraphQL schema changes, database migrations that should be run, and any new environment variables that were added. Include information on how to test the changes.
- **PR review:** at least one other engineer must approve, and the PR author must address all comments before merging. If you disagree with a comment, explain why in the PR discussion.
